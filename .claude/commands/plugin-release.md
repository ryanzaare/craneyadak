argument-hint: <نسخه، مثل 3.25.0>
---

نسخه‌ی هدف: **$ARGUMENTS** (باید N.N.N و بزرگ‌تر از نسخه‌ی فعلی باشد).

قاعده‌ی حاکم: **هرگز نتیجه‌ای را گزارش نکن که خودت ندیده‌ای** (CLAUDE.md). هر مرحله را اجرا کن و خروجی واقعی را ببین.

1. `docs/backlog.md` را باز کن و بخوان چه چیزی در این نسخه وارد شده (تغییرات افزونه از آخرین کامیت: `git diff HEAD --stat -- wordpress-plugin`). اگر تغییری در افزونه نیست، بایست و بگو.
2. پیش از bump تست کن: `php wordpress-plugin/wp-stub-harness.php`، `npm run check:plugin` و `npm run check`. اگر هرکدام قرمز است، بایست؛ bump نکن.
3. `node scripts/plugin-release.mjs $ARGUMENTS` — هدر Version و CYH_VERSION را عوض می‌کند، zip می‌سازد، zipهای قبلی را حذف می‌کند (قاعده‌ی ۴) و zip را با منبع `diff -r` می‌کند. اگر خطا داد، علت را بگو و ادامه نده.
4. مستندات: در `docs/backlog.md` هر ارجاع به شماره‌ی نسخه‌ی قبلی افزونه (مثلاً «افزونه‌ی X **و** تأیید قیمت») را به‌روز کن و یک خط برای تغییرات این نسخه بنویس. چیزی که آزموده نشده با 🔶 علامت بخورد. `npm run check` را دوباره اجرا کن (نگهبان مستندات).
5. کامیت فارسی (پیام «چرا» را بگوید، نه فقط «چه»)، با پایان `Co-Authored-By: Claude Code <noreply@anthropic.com>`. فقط فایل‌های همین انتشار را stage کن (`git status` را ببین؛ `.gitignore` و `.claude/launch.json` از کارفرما هستند و stage نمی‌شوند). هوک پیش‌کامیت `npm run check` را خودش می‌سنجد.
6. **push نکن** مگر کارفرما صریحاً گفته باشد (`git push` عمداً در ask است).
7. پایان پاسخ، گام‌های شماره‌دار برای کارفرما: «zip جدید را نصب کن»، آنچه باید در وردپرس زنده بررسی شود، و آنچه روی وردپرس زنده آزموده نشده.
